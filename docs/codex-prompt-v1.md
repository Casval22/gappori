# Codex実装依頼：がっぽりナビ v1

あなたは、このリポジトリを実装・検証するソフトウェアエンジニアです。
以下の要件に基づき、日本語のスマートフォン向けWebアプリ「がっぽりナビ」を完成させてください。
設計説明や見た目だけのモックで終わらず、実際に動くUI、計算エンジン、端末内保存、テスト、GitHub Pages公開用設定を実装してください。

まず既存ファイル、README、AGENTS.md、package.json、Git設定を確認してください。既存の実装とユーザーの変更は尊重し、無関係な削除や大規模な置き換えは避けてください。空のリポジトリなら新規作成してください。
曖昧な点は、以下の優先順位に従って保守的な仕様を選び、docs/assumptions.mdに記録して進めてください。実機の未確認事項を勝手に確定させないでください。

優先順位：
1. この依頼に明記したv1の範囲と制約。
2. 計算の正しさ、仮定・不明値・近似の明示。
3. 実機の短いBET時間で使える入力と表示。
4. パフォーマンス、保守性、見た目。

## 1. アプリの目的とv1の範囲

日本のメダルゲーム「ギョ～転！ガッポリすし」の通常版を想定する非公式のプレイ支援ツールを作る。
目的は利益の保証ではなく、「持続時間」「ワクワク度」「実機での操作負担」のバランスを比較し、好みに応じたBET候補を提示すること。

v1で実装するもの：
- 積み上げ図からネタ構成の「型」を選ぶ。
- 未登録の型を「＋」から追加する。
- 最大8種類のネタ列を、8色と列番号で識別する。
- プレイ人数を1～4人で切り替える。
- 1台の端末で全員の条件を管理し、個人別・グループ全体のBET案を計算する。
- 未確定なルール、下駄盛・舟盛のFC確率、費用、配当、選好を設定する。
- 当選確率、配当が分かる場合の収支分布、条件付きの持続時間を計算する。
- 型、設定、プレイヤー、実際に記録したプレイ履歴を端末内に保存する。
- JSONによるバックアップ・復元。
- GitHub Pagesに静的サイトとして公開できる構成。

v1では実装しないもの：
- カメラ、OCR、画像認識、QRコード読み取り。
- クラウドDB、Supabase、Firebase、サーバーAPI、認証、課金。
- 別々の端末間のリアルタイム同期、ルーム参加、WebSocket、WebRTC。
- 実機との自動連携、自動BET。
- 実測による物理抽選の偏りの学習。
- 特殊抽選、スタンプ、漁、JPなどの詳細な最適化。
- Service Workerによるオフライン起動保証。

「4人対応」は1台で4人分を扱う意味であり、4台同期ではない。同期できるような表示や機能していない参加ボタンを置かない。
v2の拡張は入力データ型と計算・保存の境界を分離することで備え、未使用のバックエンドや大量のダミー実装は作らない。

## 2. 技術スタック

採用：
- TypeScript、strict有効。
- React + Vite。
- React RouterのHashRouter。
- Tailwind CSS。
- Zustand：UIとアプリ状態の管理。
- Zod：設定・インポート・保存データの実行時検証。
- Web Worker：確率計算・探索・シミュレーション。
- localStorage：小規模な端末内保存。DB製品やIndexedDBはv1では導入しない。
- Vitest、React Testing Library、Playwright。
- npm、package-lock.json、ESLint。
- アイコンやアクセシブルな部品は必要最小限。shadcn/uiは必要な部品だけ採用してよい。

既存環境に合わせ、互換性のある安定版を採用する。バージョン番号を推測しない。Node.jsの対応LTSを選び、ローカル指定・package.json・CIで揃える。
外部AI API、APIキー、ランタイムCDN、外部フォント、解析SDKは不要。利用者の型・残高・履歴を外部送信しない。

## 3. 画面構成とモバイルUX

基本画面は「プレイ」「型の管理」「設定」「履歴・データ管理」。メインのプレイ操作を最優先にする。

### 3.1 プレイ画面

上から次の順番を基本とする。
1. アプリ名、現在のラウンド、設定への入口。
2. 人数切替：1 / 2 / 3 / 4。
3. スタイル切替：長持ち / バランス / 一撃重視 / グループ重視。
4. 型の一覧と「＋ 型を追加」。
5. 選択中の型の大きな積み上げ図。
6. P1～P4のBETカード。1人時はP1のみ。
7. 条件付き確率、推定ラベル、使用モデルの短い説明。
8. 次のラウンド・結果記録への操作。

型を1タップすると、その場で計算を開始する。毎回設定画面を通らせない。
残高や1回の上限は事前設定し、変更時のみ編集する。人数を減らしても非表示プレイヤーの設定は保持し、増やしたら復元する。
初回は少ない入力で開始可能にする。配当未入力でも型選択と確率比較は使えるようにする。

### 3.2 型の積み上げ図

- 魚名は入力しない。型は列ごとのポケット数の配列で表す。
- 表示は左から個数の少ない順、各列の底辺を揃え、1枠を1ブロックとして縦に積む。
- 列数は1～8。5列固定の実装は禁止。
- 同数の列も別のネタとして扱い、左から①～⑧の列番号を持たせる。
- 数字配列だけでなく、実機と見比べられる形を主役にする。
- 小さなカードでも個数と列の順番が読めるようにする。
- 高い列や8列の型でも、画面をはみ出さず縮尺を調整する。
- ネタの列順は入力・BET指示・配当キー・履歴で一貫させる。計算用に並べ替える場合は必ず対応を復元する。
- 同数列を勝手に入れ替えない。「同じ数ならどちらでもよい」とは扱わない。

8色の初期案：
#E69F00 / #56B4E9 / #009E73 / #F0E442 / #0072B2 / #D55E00 / #CC79A7 / #6B7280

これはアプリ独自の列色で、実機の魚や色との一致を意味しない。必ず列番号・個数・輪郭も併用する。淡い色の上の文字は十分なコントラストを持たせる。

サンプル型：
[1,2,3,4,5]
[3,3,3,3,3]
[2,2,3,3,5]
[1,1,1,1,2,2,3,4]

これらは表示確認用のサンプルであり、公式な実在型一覧ではない。必要に応じて削除できること。

### 3.3 「＋ 型を追加」

- ボトムシート等で、列の追加・削除と各列の＋／－、数字の直接入力を提供する。
- 図をリアルタイムに更新し、現在の合計と必要合計を常に表示する。
- 列は1～8、個数は正整数。小数、負数、ゼロ、9列以上、合計不一致は保存不可。
- 編集操作の途中で入力欄を勝手に並べ替えない。保存時に昇順に正規化する。
- 合計が一致したら保存操作を有効にする。編集中の不意な自動保存はしない。
- 「追加して選択」で保存と計算を一度に実行する。
- 同一モデル・同一配列の重複登録を防ぎ、既存の型を選べるようにする。
- 型の名前は任意。名前なしでも図で使えること。
- お気に入りと手動並び替えを提供するが、プレイ中に使用頻度で位置を動かさない。
- 既存型を編集しても、過去のプレイ記録の内容は変えない。

### 3.4 BET表示

魚名ではなく、例えば「下駄：②×2、⑤×1 ／ 2皿」のように指示する。
同じ図の該当列を強調し、実機でタップする順も分かるようにする。
「必要メダル」「購入皿数」「条件成立確率」「配当が分かる場合の収支」を分けて表示する。
表示する案は基本3つまで。採用案は目立たせ、詳細は展開式にする。
異なるBET組み合わせ数は1人あたり初期上限2、設定で最大3までとし、操作量を抑える。
追加BETを別表示するなら、追加前後の費用と評価を再計算し、完成形の確率を部分BETの確率として表示しない。

### 3.5 UI品質

日本語UI、片手操作、大きな文字、44px程度以上のタップ領域を設計目標にする。
360px幅から使え、8列や4人でもページ全体の横スクロールを発生させない。
キーボード操作、フォーカス表示、適切なlabel、ダイアログのフォーカス管理、reduced-motionに対応する。
絵文字だけのボタンや、色だけで区別する表示は禁止。
実機の画像・ロゴ・素材を無断で取り込まず、オリジナルの簡素な積み上げ表示を使う。

## 4. データ設計と保存

次の概念をTypeScriptの型で分離する。
- Pattern：id、ポケット構成、対応するモデル、名前、お気に入り、表示順。
- RuleProfile：ルール仮定、FC設定、単価、上限、バージョン。
- PlayerProfile：id、名前、残高、1回の上限、選好。
- BetLine：皿種、要求個数ベクトル、購入皿数、費用、配当情報。
- PayoutQuote：取得元、適用範囲、総払出枚数、数量条件、確認したラウンド。
- RoundSnapshot：ラウンドID、型、ルール、プレイヤー条件、計算・記録したBET。
- CalculationResult：結果、精度区分、仮定、警告、入力ハッシュ、探索範囲、所要時間。
- AppData：schemaVersionを持つ保存用データ。

列番号は1始まりで表示し、内部の配列添字は0始まりで統一する。変換は一箇所にまとめる。
計算エンジンにはReact、Zustand、localStorage、DOMを持ち込まない。

保存はStorageRepositoryに隔離する。保存キーはアプリ固有の名前空間を持ち、同じGitHub Pagesオリジン上の他アプリと衝突しないようにする。
保存するのは型・設定・少量の履歴。大きな確率テーブルや乱数サンプルは保存しない。
保存頻度を抑え、容量超過、保存不可、破損JSON、古いスキーマを扱う。保存できない場合も一時的な利用を続け、警告する。
破損データを説明なく上書きしない。

JSONエクスポート・インポートを実装する。インポート前にサイズ、バージョン、型、有限数、範囲を検証し、確認後に適用する。
データ全削除は確認を必要とする。「このブラウザ内だけに保存」「別端末には自動共有されない」「ブラウザのデータ削除で失われる」を説明する。

## 5. ルール設定：実機の確定仕様と仮説を混同しない

この依頼は実機の完全な公式仕様書ではない。以下は計算のための初期モデルであり、画面とdocs/assumptions.mdで明示する。

基準モデル：
- 総ポケット16、通常ネタ15、特殊1。
- 通常抽選5球、前半3球・後半2球。
- 各物理ポケットは等確率、使用済みポケットには入らない非復元抽選。
- 特殊ポケットも5球の結果には含めるが、追加抽選の報酬は含めない。
- 下駄盛は要求3貫、舟盛は要求5貫。
- 同種ネタを複数貫要求できるモデル。

総ポケット数・特殊数は設定可能にし、型の合計は総数－特殊数で検証する。実装・性能保証の範囲は総ポケット6～20、特殊0～総数－1、通常5球、ネタ1～8種類とする。3球＋2球という段階構造はv1では固定にしてよい。
設定変更により不適合になる型は削除せず、選択不可の理由を表示する。

下駄1皿5枚、舟1皿10枚、同一BET30皿までを初期の仮設定として用意してよいが、実機で確認済みと表示しない。すべて変更可能にする。
丸皿は機械が提示する条件をアプリが把握できないため、要求1～2貫・費用・配当をユーザーが登録したものだけ扱う。存在しない丸皿を自動生成しない。

特殊抽選等は「計算対象外」と表示する。実際の収支記録では追加支出・追加獲得として手入力できる。
不明な仕様を追加の固定倍率や隠れた補正率で埋めない。

## 6. 確率エンジン

### 6.1 FCなしの基準計算

ポケット数ベクトルhには特殊枠も含める。結果xの要素和を5とする。

P(X=x) = product_i C(h_i, x_i) / C(N, 5)

BETの要求rに対し、通常ネタの全列でx_i >= r_iなら条件成立。要求のない列と特殊枠も抽選の分母・状態に含める。

集約した個数ベクトルを列挙し、多変量超幾何分布の重みを付ける。個数ベクトルを等確率として扱ってはいけない。
基準16ポケットでは物理的な5ポケット集合はC(16,5)=4368通り。
このモデル内の単発当選確率・FCなしの合算配当分布は厳密計算する。最初からモンテカルロに置き換えない。

下駄と舟の要求ベクトルは、列数に応じて生成する。魚名は不要。
FCなしでは物理的に不可能な要求を除外する。FCありのモデルでは、FCで成立し得る要求を誤って除外しない。

### 6.2 共同抽選と配当分布

全員が同じ抽選結果を見る。プレイヤーごと、BETごとに別の5球を引いてはいけない。

同じ要求の皿を複数購入しても、通常抽選での当選確率は増えない。数量は費用と配当に反映する。
当たりが重なるBETを独立として合成しない。
同じプレイヤーの同一BET行は正規化してまとめる。行を分割してFC抽選回数を不正に増やせる実装にしない。

共通の結果ごとに各人の払出・純増を計算し、次を求める。
- 各人の条件成立確率。
- 誰か1人以上が成立する確率。
- 全員が成立する確率。
- 配当が分かる場合の各人・グループの収支分布。

確率の「厳密」はこの仮定したモデル内の意味。実機の実測確率と呼ばない。

## 7. フリーチョイス（FC）モデル

下駄・舟それぞれのFC獲得確率を設定可能にする。初期値はnull（不明）とし、0%と区別する。
画面入力は0～100%、内部は0～1。null、0、1を正しく処理する。

v1で実装する仮説設定：
- 獲得判定：1BET行につき1回／購入皿ごと独立に判定し1回以上獲得。
- 付与の効果：そのBET行にだけ適用、1行につき最大1個のFC。
- 効果量：選んだ列の要求を1貫分満たす／選んだ列の未充足要求を全部満たす。
- 選択可能列：前半3球で未出現の列のみ／要求が未充足の列。

これらは実機仕様の断定ではなく、比較用の仮説であることを設定画面に明記する。
複数BETや全プレイヤー共通へのFC適用はv1に含めない。この制限を隠さない。

数量nで「購入皿ごと独立・1回以上」を選んだ場合の行の獲得率：
q = 1 - (1-p)^n

行単位1回ならq=p。FCの発生は行間・プレイヤー間で独立という仮定を明示する。

前半3球を見てから対象列を決め、後半2球を引く。
選択方針は、その時点での当該BET行の条件付き当選確率を最大にする列。同率は列番号順とする。グループ効用まで含めたFC選択の大域最適性は主張しない。
後半の実際の結果を見てからFC列を選ぶ「未来を知った計算」は禁止。

前半y、後半zの確率は、次の段階的な非復元抽選として扱う。
P(y,z) = [product C(h_i,y_i) / C(N,3)]
         * [product C(h_i-y_i,z_i) / C(N-3,2)]

FCは仮想的な達成補助であり、物理的なポケットや残り球数を増減させない。
単一BETのFC込み確率はこの段階モデルで求める。
複数BETの配当分布は、共通の物理結果とFC発生を一緒に扱う。状態数が大きければ乱数seed付き近似を使ってよいが、その部分を「推定」と表示する。

FCを除外するモードを用意する。不明値がある場合はFCなしの基準結果を表示し、「FC未設定のため除外」と明示する。nullを黙って0とする実装は禁止。
任意の前半3球を入力し、FC対象の推奨を確認する簡易画面も用意する。実機でFCを獲得済みと指定した行は、獲得確率ではなく獲得済み条件で計算する。

## 8. 配当モデルと不明値の扱い

実機の公式配当式はこの依頼では与えていない。勝手に倍率表や還元率を作らない。
配当は次の3区分に分ける。
1. 不明。
2. ユーザーが実機で確認して入力した値。
3. デモ用の架空値。

「払出枚数」は元手との差分ではなく当選時の総払出。「純増」は総払出－費用と定義する。
配当は「1皿あたり、数量比例が確認済み」か「指定購入数量の合計表示値」かを明示する。
数量指定の配当を別の数量に勝手に比例換算しない。数量が変われば再入力が必要。

配当の適用キーには型の順序付き構成、皿種、要求、ルール、必要に応じて数量・ラウンドを含める。
同じ型でも次ラウンドの配当が同じとは断定しない。過去値は候補として再利用できるが、「今回未確認」を明示する。
配当未入力を0枚として収支計算しない。

配当不明の時：
- 条件成立確率、組み合わせの重複、操作量を比較する。
- 費用が分かる範囲で予算制約を反映する。
- 「確率ベースの候補」と表示する。
- 期待収支・回収率・持続回数の数値は出さない。

配当が分かる時：
- 総費用、期待払出、期待純増、純増が正になる確率、損失確率を表示する。
- 「何か当たる」と「全BETを差し引いて増える」を区別する。
- 配当が揃った候補だけを収支最適化し、「配当入力済み候補内」と明示する。

デモモードは明示的な操作でのみ開始し、画面全体に「架空配当のデモ」を表示する。現実の設定・履歴と混ざらないようにする。
デモ以外で、架空の配当を使っておすすめ順位を作らない。

## 9. BET最適化

意思決定は、要求の組み合わせ、購入数量、個人ごとの分配。
同時に「続けやすさ」「当たりの楽しさ」「途中のハラハラ」「大当たりの可能性」「実機操作量」を比較する。

制約：
- 各人の残高と1回のBET上限を超えない。
- 単価、数量単位、数量上限、異なるBET数上限を守る。
- 予算は個人別。グループ全体にメダルを自動合算しない。
- 操作時間上限を設定した場合は満たす案だけを扱う。
- 条件を満たせない場合は「購入可能な案なし」と表示する。
- 損失を取り戻すための自動増額はしない。

探索手順：
1. 単独BET候補の確率を計算。
2. 予算・操作数で候補を絞る。
3. 当たりやすい候補だけでなく、低相関の分散候補や高配当候補も残す。
4. 購入数量を含め、貪欲法・ビーム探索・局所改善などでポートフォリオを探索。
5. 共同抽選に基づく分布で個人・グループの案を評価。
6. 上位案に必要な詳細計算を追加。

候補を枝刈りしたりヒューリスティック探索をした場合は、数学的な大域最適解と呼ばない。「探索範囲内のおすすめ」と表示し、候補数・打切り条件を記録する。
当選確率の厳密性と、最適化探索の近似性は別々に表示する。

ワクワクの特徴量は説明可能な代理指標にする。
- 小当たりの頻度。
- ユーザーが設定した純増閾値以上になる確率。
- 前半3球後の条件付き成立確率qに対する4q(1-q)の期待値を、ハラハラの暫定指標にする。
- 損失確率・早期終了リスク。

これらは心理学的に確立した楽しさの測定値ではない。単に分散が大きければ楽しいとしない。
特徴量を0～1等に正規化し、持続性・ワクワク・グループ目標・操作コストをユーザーの重みで評価する。式・重み・限界はdocs/model.mdに記録する。
プリセットは実際の重み変更に接続し、見た目だけの切替にしない。

操作コストは異なるBET数、ネタ選択回数、数量変更操作などから推定する。実測時間と呼ばず、設定で調整可能にする。

グループの目標：
- 誰かが当てる。
- 全員が続ける。
- 一緒に当てる。
個人の選好も残す。4人の独立したおすすめを並べるだけではなく、共通の結果に対してグループの候補を比較する。

## 10. 持続時間のシミュレーション

残高更新は、M_next = M - actualCost + grossPayout。
配当が不足している時は実行しない。

実機の将来の型の出現分布は未確定なので、v1の持続性評価は次の限定モデルにする。
「現在の型・配当・ルールを固定し、各ラウンドを独立な抽選として反復した場合」。
この仮定を結果の近くに表示する。実機であと何分続くかの保証に見せない。

現在の選択BET構成を継続する方針で開始し、残高が減った場合の数量削減・停止の規則を明示する。実装する方針はUIに表示し、比較の途中で勝手に変えない。
試行上限Hを設け、「H回を上限とした平均プレイ回数」、中央値、K回以上継続できる確率、早期終了確率を表示する。
Hまで生存した試行は打切りとして扱い、無制限の期待寿命を計算したように表示しない。
ゲームの所要秒数をユーザーが設定した場合のみ時間換算する。

各試行は共通の物理抽選を全プレイヤーに適用する。1人でも継続できなくなるまでと、最後の1人までを区別する。
再現可能な乱数seedを使い、試行数、打切り、推定誤差または信頼区間を表示する。
見送りで消費をゼロにする案を「無限に遊べる最適戦略」として推薦しない。

## 11. 計算性能とキャンセル

型選択への表示反応は100ms程度以内、通常の軽量候補表示は1秒以内を設計目標にする。実測前に達成済みと書かない。
厳密なFC込み共同評価や持続シミュレーションは別の詳細処理として段階表示してよい。
重い処理でメインスレッドを止めない。

- WorkerはViteで解決可能なnew URL(..., import.meta.url)方式で構成する。
- requestId、ラウンドID、入力ハッシュで結果の一致を確認する。
- 型・設定・予算の変更後、古い結果を最新として表示しない。
- 古いジョブの破棄・中止・Worker再起動を適切に扱う。
- キャッシュキーには型、ルール、FC、配当、数量、予算、選好等、結果に影響する入力を含める。
- 候補数・探索幅・試行数に上限を持ち、処理途中でもUIを操作できるようにする。
- 性能不足は、探索範囲と近似を明示して調整する。正確性を黙って落とさない。

## 12. ラウンドと結果記録

型を選び直すだけで新しいプレイを実行したことにしない。ラウンドIDは明示的に管理する。
「次のラウンド」で新しい状態へ進み、古いBET結果を区別する。
推薦を表示しただけでは残高を減らさない。

結果記録で、実際のBET費用、通常払出、追加支出、追加獲得を確認し、一度だけ残高へ反映する。
履歴は型・ルール・BETのスナップショットを保存し、設定編集後も変化しないようにする。
二重押しで二重精算しない。直前の記録取消を提供し、取り消した残高を正しく復元する。
結果を入力していないものを自動的に外れ扱いしない。

## 14. 必須テスト

### 数学・状態

- 組合せ数C(16,5)=4368。
- 抽選結果の確率の総和が許容誤差内で1。
- 小さな問題で、物理ポケット全列挙と集約状態計算が一致。
- 特殊枠を含む分母と非復元抽選を正しく扱う。
- 不可能なBETの確率0。
- 同じBETを複数皿購入しても、FCなしの成立確率が変わらない。
- 同一BETをする2人の、誰かが当たる確率は単独の確率と同じ。独立式にしない。
- 1人だけ有効なグループ評価は単独評価と一致。
- 全プレイヤーの予算と操作数制約を守る。
- FC確率null、0、1、数量ごとの集約を区別。
- FC対象を後半結果に依存して選んでいないこと。
- FCの仮説設定で、条件付き結果が正しく変わること。
- 配当不明をゼロとして計算しない。
- 数量限定の配当を誤って外挿しない。
- 乱数seedを固定した推定の再現性。
- 小規模な厳密計算とMonte Carloの整合性。
- シミュレーションの停止・打切り・継続確率を扱う。
- 古いWorker結果、設定変更後のキャッシュ、二重精算を防ぐ。

数値検証用の基準ケース：
通常ネタh=[1,2,3,4,5]、特殊1、FCなし、5球。
- 舟r=[0,1,1,1,2]：240/4368 = 約5.4945054945%。
- 下駄r=[0,0,1,1,1]：2030/4368 = 約46.4743589744%。
- 舟r=[0,0,0,0,5]：1/4368 = 約0.0228937729%。
これらは指定した理論モデルのテスト値であり、実測値ではない。

### UI・保存・E2E

- 初回起動から、型選択→確率表示まで通る。
- ＋から8列の型を追加し、再読み込み後も残る。
- 不正な型を保存できず、重複を防げる。
- 1→4→1人切替で設定を保持。
- 配当なし／手入力／デモを明確に区別。
- FC設定と予算の変更で再計算。
- 型、配当、数量の対応が同数列でも崩れない。
- JSONの往復と不正JSON・未来バージョン・容量超過の処理。
- 結果記録、取消、再読み込み。
- GitHub Pages相当のサブパスで、画面遷移・再読み込み・Worker・アセットが動く。
- 360px、390px、デスクトップ幅で崩れない。
- ランタイムで外部API通信を必要としない。

Playwrightで主要画面のスクリーンショットを取得して見た目も確認する。テスト未実施を合格と報告しない。

## 15. GitHub Pages公開

静的なdistをGitHub Actionsで配信する。専用バックエンドは不要。

- vite.config.tsのbaseを、リポジトリ配下の公開パスに対応させる。
- 環境変数VITE_BASE_PATH等で明示設定でき、CIではリポジトリ名から設定できるようにする。
- ユーザー／組織のルートサイト、ローカル開発、カスタムドメインではbase='/'に切り替えられること。
- リポジトリ名・ユーザー名を架空の固定値で埋め込まない。
- HashRouterを使い、サーバー側のSPAリライトを前提にしない。
- ルート絶対パスでアセットやWorkerを参照しない。
- npm ciで再現できるlockfileを含める。
- CIはPRと既定ブランチへのpushで型検査・lint・テスト・ビルドを行う。
- デプロイは既定ブランチへのpushとworkflow_dispatchのみ。PRから公開しない。
- 公開前に必要な検証が成功するよう、ジョブの依存関係を構成する。
- GitHub公式のPages用Actionsを使用し、導入時に有効な版を確認する。
- CIはcontents: readを基本とし、公開ジョブに必要なpages: write、id-token: writeを限定する。
- github-pages環境とデプロイ競合制御を設定する。
- READMEに「Settings → Pages → Source: GitHub Actions」の手順を記載する。

この依頼ではローカル実装と公開設定の準備まで行う。リモートへのpush、リポジトリ公開範囲の変更、管理設定の変更は勝手に行わない。
公開まで実行していない場合は、公開済みと報告しない。

最低限のスクリプト：
npm run dev

READMEに次を日本語で記載する。
- アプリの目的、起動、ビルド、テスト、Pages公開。
- 1台で1～4人を扱い、端末間同期はないこと。
- データの保存場所とバックアップ。
- ルール仮定、FC仮説、配当不明時の制限。
- 理論値、推定、デモ、実測を区別していること。
- 持続時間は現在の型等を固定した条件付きシミュレーションであること。
- v1で計算しない特殊要素。
- 非公式ツールであり、配当・利益・プレイ時間を保証しないこと。

実装は、基盤→型入力→確率→設定と配当→個人最適化→4人共同評価→持続性→履歴→テスト・公開設定の順に進める。
途中で仕様書だけを出して終了しない。使える一連の流れを通し、エラーを修正してから完了報告する。
計算結果を固定のダミーデータで置き換えない。

完了時は次を報告する。
1. 実装した機能。
2. 実際に実行した検証コマンドと結果。
3. 起動・公開に必要なユーザー側の操作。
4. 未確認の実機ルール、近似、実装上の制限。
5. 未実行の検証や未達の項目があれば、その内容。

重要な受入条件：
- 通信サービスの契約や環境変数の秘密鍵なしで起動・計算できる。
- 型を選ぶと、本物の計算エンジンによる結果が出る。
- 最大8列と1～4人に対応する。
- 未知の配当を発明しない。
- 全員共通の抽選による相関を正しく扱う。
- FCの意思決定が未来の結果を参照しない。
- 実機で確認していないルールや理論値を断定しない。
- GitHub Pagesのリポジトリサブパスで動作する。
